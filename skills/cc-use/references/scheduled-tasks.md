# 在定时任务中使用 cc-use

本文只提供设计参考，不规定具体调度框架。cc-use 不负责注册 cron、launchd、systemd timer 或其他定时器，也不保存定时规则。用户和外层 Agent 应根据机器、用户身份、shell 配置、凭证来源和任务特性选择外部调度方式。

## 先明确边界

外部调度器只负责在某个时间触发任务。被触发的外层 Agent 或控制器仍然要承担 cc-use 的完整监督职责：启动内层 TUI、检查启动画面、发送短 prompt、读取屏幕快照、决定等待时间、执行验收，并在整个任务结束后调用 `finish`。

```text
cron / launchd / systemd / 其他调度器
                  ↓
        外层 Agent 或控制器
                  ↓
              cc-use
                  ↓
       tmux 中的内层 Agent
```

不要把 `scripts/cc-use` 当成无人监督的批处理执行器。helper 不理解屏幕内容，也不能判断任务是否完成、登录是否安全、更新提示应该如何处理，或多久以后应再次检查。

## 选择调度方式前要确认的问题

- 任务属于哪个系统用户，由谁拥有项目文件和凭证？
- 机器使用 Bash、zsh 还是其他登录 shell？
- PATH、API Key 和工具初始化写在哪些 shell 配置中？
- 任务运行时机器是否可能休眠、重启或离线？
- 上一次任务尚未结束时，新一次触发应跳过、排队还是并行？
- 任务需要用户登录、账号选择、动态验证码或其他人工交互吗？
- 调度器如何记录外层 Agent 的结果、错误和通知？

这些问题没有跨机器通用的唯一答案。不要让 cc-use 猜测用户环境。

## shell 与环境变量

cron、launchd 和 systemd 通常不会继承当前 Terminal 中临时设置的环境，也不会自动读取用户的交互式 shell 配置。只设置 `SHELL=/bin/bash` 也不会让 cron 自动读取 `.bash_profile` 或 `.bashrc`。

需要登录 shell 环境时，先确定任务所属用户真正配置的 shell，再使用该 shell 的登录模式启动外层任务。例如：

```bash
/bin/zsh -lc 'exec /absolute/path/to/runner'
/bin/bash -lc 'exec /absolute/path/to/runner'
```

不要为所有用户写死 `/bin/bash`。macOS 默认通常是 zsh，其他机器也可能使用 Homebrew Bash 或不同 shell。系统级实现应从用户账户信息获取 shell 和 home，而不是依赖调度器进程中可能缺失或过期的 `$SHELL`。

登录、非交互 shell 读取哪些文件取决于 shell：

| shell | 登录模式通常读取 | 通常不会自动读取 |
|---|---|---|
| Bash | `.bash_profile`、`.bash_login` 或 `.profile` | `.bashrc`，除非登录配置主动 source |
| zsh | `.zshenv`、`.zprofile`、`.zlogin` | `.zshrc` |

如果必要变量只存在于交互配置中，用户需要自行决定是调整配置位置、提供任务 wrapper，还是由外部调度系统注入变量。cc-use 不扫描 export、不拼装变量，也不自动 source 一组猜测出来的配置文件。

如果 shell 配置中使用交互判断，定时任务需要的环境变量必须位于提前返回之前：

```bash
export API_KEY="..."
export PATH="/some/path:$PATH"

case "$-" in
  *i*) ;;
  *) return ;;
esac
```

## macOS 与 Linux

| 平台机制 | 需要注意的环境和行为 |
|---|---|
| macOS LaunchAgent | 以登录用户运行，但不会自动读取 shell 配置；需要时显式调用用户登录 shell |
| macOS LaunchDaemon | 通常以 root 或指定用户运行；不能假设会读取当前用户的配置或凭证 |
| cron | 环境通常很小，不继承当前 Terminal；机器休眠期间的触发可能直接错过 |
| systemd user timer | 由用户级 systemd 管理器运行，不自动读取 shell 配置；是否补跑错过的任务由 timer 设置决定 |

macOS 上的个人任务通常更适合 LaunchAgent。需要访问受 TCC 保护的目录或应用数据时，还要单独考虑 Full Disk Access 等系统权限；环境变量正确不代表系统一定允许访问。

## session 与任务粒度

一次定时触发如果代表一个完整、独立的用户任务，就为它创建一个新的 cc-use session。这个任务内部可以连续发送多个短 prompt，并在同一个内层 Agent 对话中保留上下文。

不要因为运行时间长而清理 session。只在该次逻辑任务整体成功、最终失败、取消或确认无法继续时调用 `finish`。如果外层进程异常退出，恢复逻辑应根据外部任务记录确认 session 的归属和任务状态，再精确处理对应 session；不要按存活时长批量删除。

不同定时触发之间是否复用内层 Agent 上下文，应由上层任务设计决定。默认把互不相关的触发视为独立任务，不要为了节省启动时间而把它们混进同一个长期 session。

## 重叠执行

外部调度器必须决定上一次运行尚未结束时怎么办：

- 跳过本次触发；
- 等待并排队；
- 使用新的唯一 session 并行执行；
- 由用户确认如何处理。

cc-use 的 session 锁只防止多个操作同时修改同一个 session，不能替代业务层的防重入策略。不要让两个外层监督者同时控制同一个内层 Agent 对话。

## 无人值守时的交互边界

外层 Agent 可以处理结果明确且不会改变环境的启动交互，例如选择“暂不升级”或“继续使用当前版本”。不要自动接受升级、安装、迁移，也不要替用户选择账号、登录方式、凭证或动态验证码。

如果定时任务需要这些人工输入，应把本次执行标记为阻塞，保存必要证据，清理 cc-use session，并通过上层通知机制告知用户。不要为了让定时任务继续而降低登录或授权边界。

## 路径、日志和验收

定时环境中的工作目录和 PATH 往往不同于 Terminal。外部调度配置应明确项目目录，并尽量使用绝对路径。标准输出、标准错误、外层验收结果和通知由外部系统管理；不要把敏感环境变量或完整凭证写进日志。

定时触发不降低验收要求。内层 Agent 的最终文字仍然不能作为成功证明，外层必须检查真实文件、测试结果、命令行为或其他用户要求。

## 最小决策清单

在启用定时执行前，至少确认：

1. 外部调度器和任务所属用户；
2. 用户登录 shell、home 和环境变量来源；
3. 项目目录、命令和日志的绝对路径；
4. 凭证在非交互环境中是否可用；
5. 休眠、重启和错过触发的处理方式；
6. 重叠执行策略；
7. 阻塞或失败时的通知方式；
8. 整个任务结束后由谁调用 `finish`。
